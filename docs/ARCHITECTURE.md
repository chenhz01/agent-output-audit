# 架构：为什么要分四层

## 核心判断

**规则永远比框架好抄。** 别人想抄你，最快的路是照着规则表重写一遍（一周）；
要抄框架，他得先理解你为什么把"法律强制"和"商业惯例"分成两个轴、
为什么每个指标必须报覆盖率、为什么退出码要分三档。

所以本项目把"可抄的部分"和"难抄的部分"**物理隔开**。

## 四层

| 层 | 路径 | 谁维护 | 换垂类要改吗 |
|---|---|---|---|
| ① 引擎 | `engine/engine.py` | 技术活 | **不改** |
| ② 规则集 | `rulesets/<name>/` | 内容活 | 新建目录即可 |
| ③ 适配器 | 由规则集自带的 target schema | 内容活 | 各自定义 |
| ④ 报告 | `engine/report.py` | 技术活 | 不改 |

## 引擎的四条铁律

1. **不认识任何业务** —— 引擎不知道 ISRC、法条、音乐、电商。
   它只认：规则集声明的数据结构、严重度等级、退出码。
2. **加规则集 = 放一个目录** —— `rulesets/x/ruleset.py` 被自动发现，核心零改动。
3. **规则自己声明检查逻辑** —— 引擎只注册、调度、汇总、出报告。
4. **引擎管置信度** —— 规则可上报 `coverage`，引擎按 `confidence_floor` 统一降权，
   避免每个检查器各写一套。

## 退出码契约（对外承诺，不随规则集变化）

| 码 | 含义 |
|---|---|
| 0 | clean — 无 BLOCK 无 WARN |
| 1 | block — 存在 BLOCK |
| 2 | warn — 无 BLOCK 但有 WARN |
| 3 | **error — 规则集/引擎自身故障**（不是"检出了问题"） |

> v3 为何独立：初版把检查器异常降级成 WARN，**结果掩盖了 2 条规则静默失效**
> （`rule.get('params')` 在 Rule 对象上抛 AttributeError）。
> 「规则坏了」必须和「内容有问题」区分开，否则调用方会把 bug 当成提示忽略。

## 报告格式

| 格式 | 用途 |
|---|---|
| `text` | 人读（默认） |
| `json` | 机读，含 confidence/coverage/enforce_type |
| `sarif` | **GitHub Code Scanning 直接消费** → 别人接不接你的分界线 |
| `junit` | CI 通用测试报告 |

## 怎么证明分层是真的

**写第二个规则集，且不改引擎一行。** 只写一个 = 无法证明，那叫"一个工具"不叫"一个平台"。

本项目已有两个：`music`（20 条）、`ecommerce`（10 条）。
